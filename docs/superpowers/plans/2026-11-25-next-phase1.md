# Next version, phase 1: local dev, data store, widget frame, first pinnable widgets

Spec: the lead review, section 5 (modular dashboard) and 7 (dev environment), kept locally in
`docs/review/2026-11-25-full-review.md` (not in git: the repo is public).

## Goal

At the end of phase 1 the owner can, **locally**:

1. run the whole app (web + every `/api/*`) on `localhost`, against the production database
   **read-only**, without touching production;
2. open a page, click the **pin** on a widget, and see it on a new **MY DASHBOARD** page
   (`?page=board`), with the same live data;
3. open the widget's **settings** (cog) and choose columns (hide, show extra, reorder), top N
   rows or hand-picked rows, sort, text size and density — on the page and on the board alike;
4. use every existing page exactly as today.

Nothing reaches production until the owner says "nasaď".

## Decisions

| Question | Decision | Why |
|---|---|---|
| Where does the new code live | A long-lived branch `next`; `main` keeps receiving hotfixes, merged into `next` regularly | One codebase; cutover is a merge, rollback is a Vercel promote |
| New shell file or the same page | The same `flowers.html`, plus real ES modules beside it (`app/`, `ui/`, `widgets/`) loaded by the page | The pages keep working while panels move out one by one (review §5.7); no big-bang |
| Build step | None. Native ES modules, as `core/` today | Review §5.8 |
| Grid for the board | Phase 1: a plain CSS grid (order + width 1-12 + height). Drag and resize (GridStack, self-hosted) is phase 3 | Ship the pin/board/settings loop first; the saved layout format `{x,y,w,h}` is library-neutral |
| Where layouts and widget settings are saved | One synced key `sfl_boards` (prefs sync, now with tombstones and an outbox) | Same on every device; old keys untouched, so rollback loses nothing |
| Local DB access | `dev-server.mjs` runs every `api/*` handler locally; env from an untracked `.env.local`; pool `max: 1`; session `default_transaction_read_only=on` | Production cannot be written from local work; one connection only |
| Local writes (prefs, boards, wishlist) | Refused locally with a clear message in phase 1; `DEV_WRITES=local` (JSON file) in phase 2 if needed | Keep phase 1 small |

## Steps (each ends green: `npm test` shows `# fail 0`, committed on `next`)

1. Branch `next` from `main`. `dev-server.mjs`: run every `api/*` locally, `.env.local` (gitignored),
   read-only DB session, pool 1. Check: WORLD, SALES, FISHING and LEVELING load locally with no
   request to production `/api/*`.
2. `app/store.mjs` + tests. Route the farm fetch and `compute?section=leveling` through it.
3. `ui/table.mjs` + tests (columns, sort, top N, picked, density, text size).
4. `ui/frame.mjs` + `app/boards.mjs` + tests.
5. `widgets/fishing-age-now.mjs`: the FISHING page renders "Do sudu teď" through frame + table;
   pin adds it to `sfl_boards`; the cog edits its settings.
6. Page `?page=board`: renders the pinned widgets in a CSS grid; remove, move up/down, width.
7. `widgets/leveling-ladder.mjs` the same way.
8. Review the branch (one fresh reviewer), fix, then show it to the owner locally.

## Not in phase 1

Drag and resize (phase 3), per-widget compute `part=` (phase 4), converting the other panels
(phase 2 onwards, starting with the review's "easiest" list), the remaining phase-0 valuation fixes
(done page by page when that page's panels move), `next.html`, bundling.

## Risks

- `flowers.html` conflicts between `main` hotfixes and `next`: merge `main` into `next` after every
  release; the new code lives mostly in new files.
- Local DB load: one connection, read-only, serial; no bulk scripts against it.
- Prefs sync carries `sfl_boards`; a malformed document must never break a page: `boards.mjs`
  validates on read and falls back to empty.
